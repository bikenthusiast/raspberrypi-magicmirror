# SEN0628 gesture sensor (phase 5a)

DFRobot SEN0628: 8×8 multizone time-of-flight sensor (ST VL53L7CX) with its own
RP2040 microcontroller. Range 2 cm – 3.5 m, field of view 60° × 60°. It returns
64 distances, no image — the reason it was chosen over a camera.

Status: commissioned on the bench over UART5 (2026-10-07). Not yet in the frame.

---

## Wiring (bench)

| Sensor (PH2.0, Gravity) | Wire | Pi pin | Signal |
|---|---|---|---|
| VCC | red | **1** | 3V3 |
| GND | black | **34** | GND |
| C/R (sensor RX) | blue | **32** | GPIO 12, TXD5 |
| D/T (sensor TX) | green | **33** | GPIO 13, RXD5 |

> [!WARNING]
> **3.3 V only on the Pi.** C/R and D/T are pulled up to the board's supply.
> At 5 V supply both data lines measured **5.2 V** — that damages the Pi's GPIO.

Pin 8 (GPIO 14) stays free: the Witty Pi monitors it to detect shutdown
(see [ADR-004](adr/004-sensor-connection.md)). That's why the sensor uses UART5
instead of the primary UART.

### Mode switch

Three-way DIP switch below the connector. **Lever 1** selects the interface
(towards the "UART" label = UART); levers 2 and 3 only set the I²C address
(0x30–0x33). The switch is read at power-up only — a `sudo reboot` keeps pin 1
powered, so unplug the Witty Pi supply after changing it.

The USB-C port streams 8×8 frames regardless of the switch position
(`screen /dev/cu.usbmodem… 115200`). Useful to check the sensor without the Pi.

## Pi configuration

```bash
echo "dtoverlay=uart5" | sudo tee -a /boot/firmware/config.txt
sudo usermod -aG dialout tobiask
sudo apt install python3-serial
sudo reboot
pinctrl get 12,13      # expected: a4 ... TXD5 / RXD5
```

Loopback check without sensor: bridge pin 32 and 33 with a jumper (Pi off while
plugging), then write and read a few bytes on `/dev/ttyAMA5`.

## Protocol

From DFRobot's Arduino library (`DFRobot_MatrixLidar.cpp`), 115200 8N1:

| | Bytes |
|---|---|
| Request | `55` · length high · length low · command · arguments (length = arguments + 1) |
| Response | status (`53` ok, `63` failed) · command · length low · length high · data |
| Set 8×8 mode | `55 00 05 01 00 00 00 08` → `53 01 00 00` |
| Fetch all zones | `55 00 01 02` → `53 02 80 00` + 64 × uint16 little-endian, mm |

**Findings during commissioning:**

- Request bytes must be **written one at a time** (write + flush per byte). Sent
  in one burst, the sensor answers nothing. An extra gap between bytes is not
  needed (0–1 ms all work); the driver uses 0.2 ms as margin. DFRobot's Python port (`DFRobot_matrixLidar.py`) does exactly
  that and therefore does not work over UART; it also hard-codes `/dev/ttyAMA0`.
- The **first command after power-up** may be ignored — retry.
- After a mode switch, **wait 5 s** before fetching data (as the Arduino library does).
- Invalid zones read **4000** (firmware V1.3).
- **3.3 V supply is sufficient** (verified 2026-10-07). Part of the bench tests
  ran by mistake with VCC on pin 2 (5 V); GPIO 12/13 passed a loopback test
  afterwards. Byte-wise sending, not the supply voltage, was the fix.

Firmware: V1.3 (`SEN0628-V1.3-20250904.uf2`, flashed via BOOT + USB-C). There is
no documented way to read the installed version.

## Measurements

| Test | Result |
|---|---|
| Hand in front of the sensor | 40–65 mm across the field; a gap between fingers shows 870–950 mm |
| Pointing at the ceiling | 1.4–1.9 m, many zones invalid (4000) at that distance |

### Frame rate (`scripts/tof_bench.py`, 60 frames per row, no printing)

| Zones | Byte gap ms | fps | Mean ms | Max ms | Duplicates | Failures |
|---|---|---|---|---|---|---|
| 8×8 | 1.0 | 7.3 | 136.2 | 148.1 | 0 % | 1 |
| 8×8 | 0.5 | 7.4 | 136.0 | 136.5 | 0 % | 0 |
| 8×8 | 0.2 | 7.4 | 136.0 | 137.4 | 0 % | 0 |
| 8×8 | 0.0 | 7.4 | 136.0 | 140.3 | 0 % | 0 |
| 4×4 | 1.0 | 14.1 | 70.9 | 1893.7 | 0 % | 2 |
| 4×4 | 0.5 | 25.0 | 40.0 | 45.3 | 0 % | 0 |
| 4×4 | 0.2 | 25.0 | 40.0 | 44.5 | 0 % | 0 |
| 4×4 | 0.0 | 25.0 | 40.0 | 44.7 | 0 % | 0 |

- The rate is fixed by the sensor firmware: **136 ms per 8×8 frame, 40 ms per
  4×4 frame**, independent of byte gap and terminal output. Each request waits
  for the next fresh frame (no duplicates).
- The 4×4 / 1.0 ms row includes one ~1.9 s stall right after the mode switch
  (two timeouts); treat it as a start-up outlier, not a gap effect.
- **Decision for gestures: 4×4 at 25 fps.** A swipe (200–400 ms) spans 5–10
  frames instead of 1–3. 8×8 stays available for static hand poses later.

## Orientation and gesture data (08.10.2026)

- Reference orientation: **USB-C socket facing down**, sensor window facing the user.
- In this orientation the 4x4 grid is mirrored horizontally: **column 1 = the user's right**.
  - `swipe_left` (user's view) -> centroid column increases (1 -> 4)
  - `swipe_right` -> centroid column decreases (4 -> 1)
- (Rotated 90°, rows instead of columns carried the swipe — keep the orientation fixed when mounting.)
- Frame rate in practice: 4x4 at ~17 fps (60 ms); bench showed 25 fps, cause unknown, sufficient for swipes.
- Recordings: `data/gestures_v2/{swipe_left,swipe_right,none}`, 10 takes each, 3 s.
- Offline rule (first prototype, now `scripts/gesture.py --replay`): hand zone = <= 500 mm and >= 80 mm in front of the
  background; >= 3 hand zones per frame; swipe = centroid moves >= 2 columns within 1.2 s.
  - Result on v2 (thresholds fixed from v1, i.e. unseen data): swipe_left 10/10, swipe_right 6/10,
    none 0/10 false triggers. Misses: hand at 40–50 cm (too few zones), hand already in view at start.
- Live detector `scripts/gesture.py` (same rule, adaptive per-zone background, 1.5 s lockout,
  `--replay` for recorded takes, `--exec` hook). Defaults tuned on v2: near 600 mm, delta 60 mm,
  min 3 zones, travel 2 columns in 1.2 s -> replay: swipe_left 10/10, swipe_right 9/10,
  none 40/40 (v1 + v2) without false trigger. Tuned on the same data -> confirm live.

### Target distance 60–80 cm (v3, 08.10.2026)

- Recordings `data/gestures_v3_4x4` and `data/gestures_v3_8x8`, hand at ~50–70 cm, body at ~70–85 cm.
- Best rule settings found by grid search (optimistic, tuned on the same 30 takes each):
  - 4x4: 15/20 swipes, 0–1/10 false (near 1000, delta 60, min 3 zones, travel 0.35, window 1.8 s)
  - 8x8: 14/20 swipes, 0/10 false (band 100) -- many zones invalid at 70–80 cm, only ~7 fps
- New defaults in gesture.py = the 4x4 far setting; on the older close-range data it still gets
  18/20 swipes, 35/39 detected/missed captures, 3/50 false.
- Limits: 4x4 zones are ~20 cm wide at 70 cm (hand fills half a zone); hand only 15–25 cm in
  front of the body; static object at ~31–36 cm bottom-left in the test setup.
- `--band` (only zones near the nearest object count) helps at close range (missed 1/12 -> 8/12).
